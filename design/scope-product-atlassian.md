## 1. Overview

**Purpose**: Structure product strategy, requirements, and decisions for long-lived products built by agentic teams.

**Design Principles**:
- **Backend agnostic**: Works with Confluence, file-based, SharePoint, Notion
- **Markdown-based**: No macros or ADF generation (error-prone for LLMs)
- **Progressive disclosure**: Start with single pages, split when topics exceed 300 words
- **Agent-managed structure**: Auto-generate overview and parent pages
- **Token efficient**: Agents load guides only when maintaining docs

**Target Products**: 5+ year lifespan, 50-200 epics, multiple features and capabilities

---

## 2. Why Atlassian Blueprint Pattern

### Industry Standard Alignment

Atlassian Confluence Blueprint is the most widely adopted product documentation pattern in enterprise software:
- **Market dominance**: Used by 60%+ of Fortune 500 companies
- **Proven scalability**: Supports products from 10 to 1000+ features
- **Clear structure**: Strategy → Definition → Reference → Decisions
- **Team familiarity**: Product Owners recognize the pattern

### Benefits for Agentic Teams

1. **Clear information architecture**: Agents know where content lives (no guessing)
2. **Progressive disclosure**: Load only what's needed (token efficient)
3. **Separation of concerns**: Product (PO) vs Technical (Architect) documentation
4. **Living documentation**: Always current, no version drift
5. **Decision traceability**: PDR links decisions to epics

## 3. Adaptation for Agent Teams

### Key Differences from Standard Blueprint

| Aspect | Standard Confluence | SCOPE Adaptation |
|--------|---------------------|------------------|
| **Format** | ADF (Atlassian Document Format) | Markdown (backend-agnostic) |
| **Macros** | Heavy use (child page list, toc) | None (manual summaries + auto-generation) |
| **Page creation** | Manual via UI | Agent-driven via MCP |
| **Progressive disclosure** | Optional | Mandatory (300-word rule) |
| **Guide loading** | N/A | Agent self-awareness (PO/Architect only) |

### Backend-Agnostic Design

**No assumptions about backend capabilities:**
- Tags/labels for queries (all backends support)
- Markdown links (converted by MCP server if needed)
- No macros or ADF-specific features
- Manual summaries on parent pages (not auto-generated by backend)

**Supported backends:**
- Confluence (via Atlassian MCP or Sooperset MCP)
- File-based (markdown files in Git)
- SharePoint (if MCP available)
- Notion (if MCP available)

## 5. Progressive Disclosure

### The 300-Word Rule

**Rule**: When any single topic exceeds 300 words (~225 tokens), create a child page.

**Rationale**:
- Parent pages remain scannable (1-2 screens)
- Agents fetch child pages only when needed (token efficiency)
- Deep context preserved without bloating main pages

### When to Split

**Product Definition:**
- Starts as single page with all use cases
- When use case flow exceeds 300 words → create child page
- Example: "Dashboard Analytics" use case with 15-step flow (450 words) → child page

**Product Reference:**
- Always has 4 children (created during PRD development)
- Children can have their own children if topics exceed 300 words
- Example: "API Integrations" has 5 integrations, each 400 words → 5 child pages under APIs & Integrations

**Product Decisions Record:**
- PDR entries on main page (100-150 words per decision)
- Decision justification >300 words → child page
- Example: "Pricing Model Analysis" with 4 strategies and market research (600 words) → child page

### Agent-Managed vs Manual Pages

| Page Type | Management | Content |
|-----------|------------|---------|
| Product Overview | **Auto-generated** | Summary + links to 4 main pages |
| Product Strategy | Manual | Product Owner writes |
| Product Definition | Manual (parent) | Product Owner writes |
| Use Case (child) | Manual | Product Owner writes when split |
| Product Reference (parent) | **Auto-generated** | Summary + links to 4 children |
| Reference children | Manual | Product Owner writes (always created) |
| Product Decisions Record | Manual | Product Owner writes |

**Content**:

## 7. Auto-Generated Pages

### 7.1 How Auto-Generation Works

**Trigger**: project-documentation skill updates when product pages created/modified

**Process**:
1. Skill detects product page creation/update
2. Queries backend for all product pages (metadata only)
3. Generates markdown with links and summaries
4. Updates Product Overview and Product Reference (parent)

**Manual override**: Product Owner can add custom summary text (preserved during auto-updates)

### 7.2 Product Overview Auto-Generation

**When updated**:
- Product Strategy created/updated
- Product Definition created/updated
- Product Reference created/updated
- Product Decisions Record created/updated

**Generated content**:
- Links to 4 main pages (Strategy, Definition, Reference, PDR)
- Brief description of each page's purpose

**Preserved content**:
- Custom summary added by Product Owner (between <!-- markers -->)

### 7.3 Product Reference Parent Auto-Generation

**When updated**:
- Any of 4 reference children created/updated
- Feature Catalog, Terminology, UI & Workflows, APIs & Integrations

**Generated content**:
- Links to 4 required children
- Brief description of each child's purpose

**Preserved content**:
- Custom summary added by Product Owner (between <!-- markers -->)

## 8. Agent Access Patterns

### 8.1 Who Loads the Guide

**Load product-guide-atlassian.md:**
- Product Owner Agent (maintains all product docs)
- Any Architect Agent (needs full structure for epic refinement)

**Do NOT load guide:**
- Developer Agent (gets URLs from epic docs)
- SDET Agent (uses Rovo search for specific use cases)
- Security Reviewer Agent (gets URLs from epic ADR)
- DevOps Agent (doesn't access product docs)

**How they know**: Agent self-awareness from system prompt

### 8.2 Access Methods Without Guide

**Direct URLs** (most common):
- Architect links relevant product pages in epic documentation
- Developer/SDET click URLs from epic docs
- Example: Epic Details contains "Implements use case: [Dashboard Analytics](https://...)"

**Rovo Search** (when exploring):
```
SDET: search("use case for dashboard analytics")
→ Returns summary + URL to use case page
```

**MCP Fetch** (when page ID known):
```
fetch(id="123456789")  # Page ID from URL or previous search
→ Returns full page content
```

### 8.3 Token Savings by Agent

| Agent | Guide Loaded? | Access Method | Tokens Saved |
|-------|---------------|---------------|--------------|
| Product Owner | Yes (2k) | Full guide + all pages | 0 |
| Architect | Yes (2k) | Full guide + all pages | 0 |
| Developer | No | URLs from epic docs | **2k** |
| SDET | No | Rovo search | **2k** |
| Security Reviewer | No | URLs from epic docs | **2k** |
| DevOps | No | N/A (doesn't access) | **2k** |

**Per-operation savings**: 2k tokens for non-maintainer agents

## 9. Token Efficiency

### 9.1 Guide Loading Strategy

**Problem**: Product guide is 8kB (~2k tokens)

**Solution**: Load only for agents who maintain documentation

**Implementation**:
```python
# In project-documentation skill
if i_am_product_owner or i_am_architect:
    load_guide("product-guide-atlassian.md")  # 2k tokens
else:
    # Access pages via URLs or Rovo search
    pass
```

### 9.2 Progressive Disclosure Benefits

**Without progressive disclosure** (single page):
- Product Definition: 3000 words (~2250 tokens)
- Architect loads entire page even if only needs 1 use case

**With progressive disclosure** (parent + children):
- Product Definition parent: 800 words (~600 tokens)
- Use Case child: 400 words (~300 tokens)
- Architect loads parent (600 tokens), fetches specific use case child (300 tokens) = 900 tokens
- **Savings: 1350 tokens (60%)**

### 9.3 Auto-Generated Pages Benefits

**Without auto-generation**:
- Product Owner manually maintains overview page
- Links break when pages renamed
- Summaries become stale

**With auto-generation**:
- Links always current
- Structure reflects reality
- Product Owner focuses on content, not maintenance

## 10. Workflow Examples

### 10.1 Product Owner Creating Product Strategy

```
1. Product Owner Agent spawned with task: "Create product strategy"

2. Agent self-identifies: "I am Product Owner Agent"
   → Loads product-guide-atlassian.md (2k tokens)

3. Agent reads guide section: "Product Strategy"
   → Understands structure: Vision, Markets, Problems, Scope, Competition

4. Agent prompts user:
   - "What is the product vision?"
   - "Who are the target market segments?"
   - "What customer problems does this solve?"
   - "What is explicitly out of scope?"
   - "Who are the main competitors?"

5. Agent drafts strategy content following template

6. Agent presents draft to user for validation

7. Agent calls project-documentation skill:
   create_page(
     tags=["product", "strategy"],
     title="Product Strategy",
     content=strategy_content
   )

8. Skill auto-updates Product Overview with link to new strategy page
```

### 10.2 Architect Reading Product Pages During Epic Refinement

```
1. Architect Agent spawned with task: "Refine epic SCOPE-42"

2. Agent self-identifies: "I am Software Architect Agent"
   → Loads product-guide-atlassian.md (2k tokens)

3. Agent needs product context:
   → Loads Product Strategy (600 tokens)
   → Loads Product Definition parent (750 tokens)
   → Identifies relevant use case: "Dashboard Analytics"
   → Loads Use Case: Dashboard Analytics child (300 tokens)

4. Agent creates epic documentation:
   - Epic Details: Links to "Dashboard Analytics" use case
   - Epic Architecture: Designs components for dashboard
   - Epic ADR: Architectural decisions

5. Developer implementing story reads Epic Details:
   - Sees link to "Dashboard Analytics" use case
   - Clicks link → Opens in browser
   - No guide loading needed (0 tokens)
```

### 10.3 SDET Finding Use Cases for E2E Tests

```
1. SDET Agent spawned with task: "Create e2e test plan for epic SCOPE-42"

2. Agent self-identifies: "I am SDET Agent"
   → Does NOT load product guide (0 tokens saved: 2k)

3. Agent needs to understand use cases:
   → Uses Rovo search: "use case dashboard analytics"
   → Results:
      - Use Case: Dashboard Analytics (https://...)
      - Summary: "User views dashboard with real-time metrics..."

4. Agent clicks URL or fetches by ID:
   → Loads Use Case: Dashboard Analytics (300 tokens)

5. Agent creates e2e test scenarios based on use case flow

Total tokens: 300 (vs 2300 with guide loading)
Savings: 2000 tokens (87%)
```
